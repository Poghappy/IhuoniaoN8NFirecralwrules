## 📖 文档目的

本文档为团队成员提供 Cursor IDE 配置的使用指南，确保所有成员遵循统一的配置规范，提高协作效率。

## 🚀 快速开始

### 新成员入职清单

如果你是新加入的团队成员，请按照以下步骤操作：

- [ ] 1. 克隆项目到本地
- [ ] 2. 安装 Cursor IDE（最新版本）
- [ ] 3. 阅读本文档（`TEAM_GUIDE.md`）
- [ ] 4. 阅读 `.cursor/README.md` 了解配置结构
- [ ] 5. 阅读 `.cursor/STRUCTURE_GUIDE.md` 了解最佳实践
- [ ] 6. 运行健康检查：`./scripts/check-cursor-config.sh`
- [ ] 7. 开始使用 Cursor 进行开发

### 5 分钟快速了解

1. **配置位置**: 所有 Cursor 配置都在项目根目录的 `.cursor/` 目录
2. **规则文件**: AI 行为规则在 `.cursor/rules/` 目录，使用 `.mdc` 扩展名
3. **索引排除**: `.cursorignore` 文件控制哪些文件不被 AI 索引
4. **提示词模板**: 常用提示词在 `.cursor/prompts/` 目录
5. **项目上下文**: 项目背景信息在 `.cursor/context/` 目录

## 📋 核心规则

### 1. 单一配置源原则 ⭐ 最重要

**DO**:

- ✅ 只在项目根目录的 `.cursor/` 维护配置
- ✅ 所有规则文件放在 `.cursor/rules/`
- ✅ 使用 Git 跟踪配置变更

**DON'T**:

- ❌ 不要在子目录创建 `.cursor/` 目录
- ❌ 不要在其他位置创建 `.mdc` 文件
- ❌ 不要复制配置文件到多个位置

**为什么？**

- 避免配置冲突
- 便于维护和更新
- 确保团队使用相同的配置

### 2. 规则文件命名规范

**命名格式**:

```text
[优先级前缀-]功能描述.mdc

示例：
- 00-ai-team-core.mdc        # 数字前缀表示优先级
- 5s-agile.mdc                # 功能描述
- chinese-output.mdc          # 使用连字符分隔
- news-collector-usage.mdc    # 多个单词用连字符
```

**命名要求**:

- 使用小写字母
- 使用连字符 `-` 分隔单词
- 描述性强，见名知意
- 可选的数字前缀表示优先级（00-99）

### 3. 规则文件格式规范

**标准格式**:

```markdown
---
alwaysApply: true                    # 是否始终应用
description: 规则描述                # 规则说明
globs: ["**/*.md"]                   # 适用的文件类型（可选）
---

# 规则标题

## 核心原则

- 原则1
- 原则2

## 详细说明

具体的规则内容...

## 示例

### 正确示例 ✅

```示例代码```

### 错误示例 ❌

```错误代码```
```

**格式要求**:

- 使用 YAML 前置元信息（可选但推荐）
- 使用 Markdown 格式编写
- 包含清晰的标题和章节
- 提供正确和错误的示例对比

## 🔧 常见操作指南

### 添加新规则

**步骤**:

1. **确定规则用途**
   - 明确规则要解决什么问题
   - 确定规则的适用范围

2. **创建规则文件**

```bash
cd .cursor/rules
touch new-rule-name.mdc
```

3. **编写规则内容**
   - 参考现有规则文件的格式
   - 包含清晰的说明和示例
   - 添加 YAML 前置元信息

4. **测试规则**
   - 重启 Cursor 或重新加载窗口
   - 测试 AI 是否按照规则行为
   - 验证规则是否生效

5. **提交变更**

```bash
git add .cursor/rules/new-rule-name.mdc
git commit -m "feat: 添加新规则 - 规则描述"
git push
```

### 修改现有规则

**步骤**:

1. **找到规则文件**

```bash
ls .cursor/rules/
```

2. **编辑规则**
   - 使用 Cursor 或其他编辑器打开
   - 修改规则内容
   - 保持格式一致

3. **测试修改**
   - 重新加载 Cursor 窗口
   - 验证修改是否生效

4. **提交变更**

```bash
git add .cursor/rules/modified-rule.mdc
git commit -m "fix: 更新规则 - 修改说明"
git push
```

### 删除过时规则

**步骤**:

1. **确认规则已过时**
   - 与团队讨论
   - 确保没有依赖

2. **删除文件**

```bash
rm .cursor/rules/old-rule.mdc
```

3. **更新文档**
   - 在 `.cursor/README.md` 中移除相关说明
   - 更新 `.cursor/STRUCTURE_GUIDE.md`

4. **提交变更**

```bash
git add .cursor/rules/
git add .cursor/README.md
git commit -m "chore: 删除过时规则 - 规则名称"
git push
```

### 使用提示词模板

**步骤**:

1. **浏览可用模板**

```bash
ls .cursor/prompts/
cat .cursor/prompts/README.md
```

2. **复制模板内容**
   - 打开需要的模板文件
   - 复制提示词内容

3. **修改参数**
   - 根据实际情况修改占位符
   - 填入具体的代码或文件路径

4. **使用提示词**
   - 粘贴到 Cursor 对话框
   - 等待 AI 响应

### 添加项目上下文

**步骤**:

1. **创建上下文文档**

```bash
cd .cursor/context
touch project-overview.md
```

2. **编写上下文内容**
   - 项目概览
   - 架构设计
   - 技术栈
   - 编码规范

3. **在开发中使用**

```text
@context/project-overview.md
请根据项目架构设计新功能
```

## 🤝 团队协作规范

### 配置变更流程

**流程图**:

```text
1. 发现需求
   ↓
2. 团队讨论
   ↓
3. 创建/修改规则
   ↓
4. 本地测试
   ↓
5. 提交 PR
   ↓
6. 代码审查
   ↓
7. 合并主分支
   ↓
8. 通知团队
```

**详细步骤**:

1. **发现需求**
   - 在开发中发现 AI 行为需要改进
   - 团队成员提出新的规则需求

2. **团队讨论**
   - 在团队会议或聊天群中讨论
   - 确认规则的必要性和范围
   - 达成共识后再实施

3. **创建/修改规则**
   - 按照规范创建或修改规则文件
   - 编写清晰的说明和示例
   - 遵循命名和格式规范

4. **本地测试**
   - 在本地环境测试规则
   - 确保规则按预期工作
   - 运行健康检查脚本

5. **提交 PR**
   - 创建功能分支
   - 提交配置变更
   - 编写清晰的 PR 描述

6. **代码审查**
   - 至少一名团队成员审查
   - 检查规则的合理性
   - 验证格式和命名规范

7. **合并主分支**
   - 审查通过后合并
   - 删除功能分支

8. **通知团队**
   - 在团队群中通知变更
   - 说明新规则的用途
   - 提醒团队成员拉取最新代码

### 冲突解决

**场景 1: 多人同时修改同一规则**

**解决方案**:

1. 沟通协调，确定谁先提交
2. 后提交者需要合并最新代码
3. 解决冲突后再提交

**场景 2: 规则之间存在冲突**

**解决方案**:

1. 识别冲突的规则
2. 团队讨论优先级
3. 调整规则内容或删除冲突规则
4. 更新文档说明

**场景 3: 本地配置与远程不一致**

**解决方案**:

1. 拉取最新代码：`git pull`
2. 运行健康检查：`./scripts/check-cursor-config.sh`
3. 重启 Cursor IDE
4. 如有问题，联系团队成员

## 🐛 常见问题

### Q1: 规则不生效怎么办？

**A**:

1. 检查规则文件格式是否正确
2. 重启 Cursor IDE 或重新加载窗口
3. 检查规则文件是否在 `.cursor/rules/` 目录
4. 查看 Cursor 控制台是否有错误信息

### Q2: 如何临时禁用某个规则？

**A**:

1. 在规则文件的 YAML 前置元信息中设置 `alwaysApply: false`
2. 或者临时移动规则文件到其他目录
3. 重新加载 Cursor 窗口

### Q3: 可以在个人项目中使用不同的配置吗？

**A**:

- 团队项目必须使用统一配置
- 个人项目可以自定义配置
- 不要将个人配置提交到团队项目

### Q4: 如何贡献新的规则？

**A**:

1. 按照团队协作流程创建 PR
2. 在 PR 中详细说明规则用途
3. 提供使用示例和测试结果
4. 等待团队审查和反馈

### Q5: 配置文件太多，如何管理？

**A**:

1. 使用数字前缀表示优先级
2. 按功能分类命名
3. 定期清理过时规则
4. 保持规则简洁明了
